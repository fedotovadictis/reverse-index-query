# Решение

## Цель проекта

Цель проекта — реализовать упрощённый поисковый индекс событий и сравнить его работу с обычным полным перебором.

В рамках работы были реализованы:

- генерация тестовых данных;
- чтение событий из JSONL;
- построение обратного индекса;
- выполнение запросов с операторами `TERM`, `AND` и `OR`;
- сравнение результатов поиска через индекс и полного перебора;
- unit-тесты и benchmark-тесты.

---

## Формат входных данных

События хранятся в формате JSONL, где каждая строка представляет собой отдельное событие.

Пример:

```json
{
  "id": 20,
  "timestamp": "2025-12-19T15:00:00Z",
  "user_id": "user_4024",
  "department": "dev",
  "action": "copy_file",
  "channel": "email",
  "file_ext": "pdf",
  "destination_type": "external",
  "severity": "medium"
}
```

Для поиска используются поля:

- `user_id`
- `department`
- `action`
- `channel`
- `file_ext`
- `destination_type`
- `severity`

---

## Как работает программа

После чтения файла строится обратный индекс.

Для каждого значения поля хранится список ID событий, в которых это значение встречается.

Например:

```text
department

dev -> [7, 9, 11, 15, 16, 17, 20]
```

или

```text
file_ext

pdf -> [3, 6, 9, 12, 20]
```

После построения индекса списки ID сортируются. Благодаря этому операции `AND` и `OR` можно выполнять быстрее.

---

## Выполнение запросов

Запрос хранится в виде дерева.

Поддерживаются три операции.

### TERM

Возвращает список ID по указанному полю и значению.

Например:

```text
department = dev
```

### AND

Сначала выполняется левая и правая часть запроса.

После этого два списка ID пересекаются.

Для этого используется алгоритм двух указателей, который проходит по обоим спискам один раз.

### OR

Работает похожим образом.

Из двух списков формируется один общий список без повторяющихся ID.

---

## Сравнение со scan

В программе есть два способа поиска:

- `scan` — полный просмотр всех событий;
- `index` — поиск по обратному индексу.

Для проверки реализована команда `compare`.

Она выполняет один и тот же запрос двумя способами и сравнивает полученные ID.

На контрольном наборе использовался запрос:

```text
department = dev AND file_ext = pdf
```

Оба способа вернули одинаковый результат:

```text
matched_ids = [9, 20]
```

Поэтому можно сделать вывод, что поиск по индексу работает корректно.

---

## Сложность

Основные операции имеют следующую сложность:

- построение индекса — `O(N)`;
- `TERM` — `O(1) + O(k)`;
- `AND` — `O(n + m)`;
- `OR` — `O(n + m)`;
- полный перебор (`scan`) — `O(N)`.

---

## Плюсы и ограничения

Построение индекса требует дополнительной памяти, но после этого поиск выполняется быстрее.

Если выполнить всего один запрос по небольшому файлу, полный перебор может оказаться быстрее, так как индекс ещё нужно построить.

В текущей реализации поддерживаются только операторы `TERM`, `AND` и `OR`. Оператор `NOT` и строковый язык запросов не реализованы.

Индекс хранится полностью в оперативной памяти, поэтому после изменения данных его необходимо построить заново.

## Benchmark

Для проверки производительности были написаны benchmark-тесты операций `Intersect` и `Union`.

В тестах использовались два отсортированных списка по 100 000 элементов.

Результаты:

```text
BenchmarkIntersect-16    233323 ns/op
BenchmarkUnion-16        868554 ns/op
```

Тестирование выполнялось на компьютере:

```text
OS: Windows
Architecture: amd64
CPU: 13th Gen Intel(R) Core(TM) i5-13400F
```

---

## Обработка ошибок

Для запросов реализована проверка корректности. Если запрос составлен неправильно или используется неизвестный оператор, программа сообщает об ошибке.

## Что можно улучшить

Если развивать проект дальше, можно добавить:

- строковый язык запросов;
- оператор `NOT`;
- оптимизацию порядка пересечения списков;
- оценку используемой памяти;
- дополнительные тесты для очень больших файлов;
- обработку дублирующихся ID и других некорректных входных данных.

---

## Итог

В ходе работы был реализован обратный индекс для поиска по журналу событий.

Программа умеет генерировать тестовые данные, читать события из JSONL, выполнять поиск двумя способами и сравнивать результаты.

Также были написаны unit-тесты и benchmark-тесты.

Контрольный запуск показал, что поиск по индексу возвращает те же результаты, что и полный перебор, но позволяет выполнять повторные запросы быстрее.
