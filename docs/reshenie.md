# Решение

## Цель проекта

Цель проекта — реализовать упрощённый поисковый индекс для журнала событий и сравнить его работу с обычным полным перебором (`scan`).

В рамках проекта были реализованы:

- генерация тестовых данных;
- чтение событий из JSONL;
- построение обратного индекса;
- выполнение запросов через полный перебор (`scan`) и через индекс (`index`);
- поддержка запросов в формате JSON и строкового языка запросов;
- операции `TERM`, `AND` и `OR`;
- сравнение результатов двух способов поиска;
- оценка времени выполнения и используемой памяти;
- unit-тесты, benchmark-тесты и интеграционные CLI-тесты.

---

# Формат входных данных

События хранятся в формате JSONL, где каждая строка представляет отдельное событие.

Пример:

```json
{
  "id": 20,
  "timestamp": "2025-12-19T15:00:00Z",
  "user_id": "user_4024",
  "department": "dev",
  "action": "copy_file",
  "channel": "email",
  "file_ext": "pdf",
  "destination_type": "external",
  "severity": "medium"
}
```

Для поиска используются поля:

- `user_id`
- `department`
- `action`
- `channel`
- `file_ext`
- `destination_type`
- `severity`

---

# Как работает программа

После чтения файла строится обратный индекс.

Для каждого значения каждого индексируемого поля хранится список ID событий, в которых встречается данное значение.

Например:

```text
department

dev -> [7, 9, 11, 15, 16, 17, 20]
```

или

```text
file_ext

pdf -> [3, 6, 9, 12, 20]
```

После построения индекса каждый posting list:

- сортируется по возрастанию;
- очищается от повторяющихся ID.

Это позволяет быстро выполнять операции пересечения и объединения.

---

# Выполнение запросов

Запрос представляется в виде дерева.

Поддерживаются три операции.

## TERM

Возвращает список ID для заданного поля и значения.

Например:

```text
department = dev
```

---

## AND

Выполняется поиск левой и правой части запроса.

После этого результаты пересекаются алгоритмом двух указателей.

Перед пересечением posting lists сортируются по длине, поэтому сначала обрабатываются самые короткие списки. Это уменьшает объём промежуточных результатов и ускоряет выполнение сложных запросов.

---

## OR

Выполняется поиск левой и правой части запроса.

После этого формируется объединение двух отсортированных списков без повторяющихся ID.

---

# Строковый язык запросов

Кроме JSON-запросов программа поддерживает строковый язык запросов через параметр:

```text
--query-string
```

Поддерживаются:

- операторы `AND` и `OR`;
- круглые скобки;
- стандартный приоритет операций (`AND` выше `OR`);
- любой регистр операторов (`AND`, `and`, `And` и т.д.);
- произвольное количество пробелов.

Пример:

```text
department=dev AND (file_ext=pdf OR file_ext=docx)
```

Строковый запрос преобразуется в дерево запросов, после чего выполняется тем же механизмом, что и JSON-запрос.

---

# Выполнение поиска

Программа поддерживает два способа поиска.

## Scan

Последовательно просматриваются все события.

Для каждого события проверяется соответствие запросу.

Сложность такого поиска составляет `O(N)`.

---

## Index

Сначала строится обратный индекс.

После этого поиск выполняется только по posting lists соответствующих полей.

Для повторных запросов этот способ значительно быстрее полного перебора.

---

# Ограничение размера результата

Если найдено очень большое количество совпадений, программа сохраняет в результат не более первых **1000** ID.

При этом:

- `matched_count` содержит полное количество найденных событий;
- `matched_ids` содержит первые 1000 ID;
- поле `truncated` показывает, был ли список сокращён.

Это позволяет избежать создания слишком больших JSON-файлов.

---

# Сравнение scan и index

Для проверки корректности реализована команда:

```text
compare
```

Она:

- выполняет один и тот же запрос двумя способами;
- сравнивает полученные ID;
- показывает элементы, которые есть только в одном из результатов;
- измеряет время выполнения;
- оценивает объём памяти индекса.

Если результаты отличаются, команда завершается ошибкой.

---

# Сложность алгоритмов

Основные операции имеют следующую асимптотическую сложность.

| Операция | Сложность |
|----------|-----------|
| Построение индекса | `O(N)` |
| TERM | `O(1) + O(k)` |
| AND | `O(n + m)` |
| OR | `O(n + m)` |
| Полный перебор | `O(N)` |

где:

- `N` — количество событий;
- `k` — количество найденных документов;
- `n` и `m` — размеры posting lists.

Для проверки производительности был выполнен запуск на наборе из **1 000 000 событий**.

Получены следующие результаты.

| Показатель | Значение |
|------------|---------:|
| Количество событий | 1 000 000 |

| Scan | 24.03 ms |

При этом результаты поиска полностью совпали:

- Results equal: `true`
- Only in scan: `[]`
- Only in index: `[]`

# Обработка ошибок

Программа проверяет корректность входных данных и сообщает об ошибках в следующих случаях:

- неизвестное поле запроса;
- неизвестный оператор;
- синтаксическая ошибка строкового запроса;
- отсутствие обязательных параметров командной строки;
- одновременное использование `--query` и `--query-string`;
- некорректный JSONL;
- слишком длинная строка JSONL;
- ошибка чтения файла событий с указанием номера строки.

# Плюсы и ограничения

## Преимущества

- быстрый поиск после построения индекса;
- одинаковые результаты поиска через `scan` и `index`;
- поддержка строкового языка запросов;
- поддержка сложных логических выражений со скобками;
- автоматическое удаление повторяющихся ID;
- ограничение размера выходного результата;
- оценка времени выполнения и памяти индекса.

## Ограничения

- оператор `NOT` не реализован;
- индекс полностью хранится в оперативной памяти;
- после изменения данных индекс необходимо построить заново.

# Итог

В ходе работы был реализован обратный индекс для поиска по журналу событий.

Программа умеет:

- генерировать тестовые данные;
- читать события из JSONL;
- выполнять поиск полным перебором и через обратный индекс;
- принимать запросы как в формате JSON, так и в виде строкового выражения;
- сравнивать результаты двух способов поиска;
- оценивать время выполнения и объём памяти индекса;
- корректно обрабатывать ошибочные входные данные.

Проведённые тесты подтвердили корректность реализации: результаты `scan` и `index` полностью совпадают как на контрольных данных, так и на наборе из одного миллиона событий, при этом поиск по индексу после его построения выполняется значительно быстрее полного перебора.
